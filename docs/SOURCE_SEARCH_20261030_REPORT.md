## 为什么总耗时大于来源耗时合计

同一首《活着》`1ww8Qq9GU6VxO293E2najn` 三次预加载均为 review、均执行 5 个查询变体：

| 统计结束时间（UTC） | 总耗时 | 来源秒数之和 | 两者差值 |
| --- | ---: | ---: | ---: |
| 08:25:59 | 74.025s | 47.741s | 26.284s |
| 08:29:13 | 95.340s | 43.814s | 51.526s |
| 08:32:42 | 72.449s | 34.491s | 37.958s |

这不是固定计时翻倍，也不是“每个来源请求两遍”就能解释。`sources.seconds` 只包住 `probe → lookupWithTimeout`，来源还会并发，不能把它们的和当作整个搜索的墙钟时间。`totalSeconds` 从会话调用 search 前计到其返回，还覆盖目录元数据、五个变体的串行推进、候选反复匹配、预览回调、归并与读音补全。

已确认的额外工作路径：`safePreviewCandidates → acceptCandidate → enrichCandidate → LyricsLayerEnricher.enrich`；正式收集候选还会再次走 `acceptCandidate`，且它在检查字典中是否已有同一候选之前就补全读音。补全逻辑将汉字也纳入日语脚本判断，逐行调用本机 MeCab，没有在此入口复用整版结果。

用该候选实际公开正文做一次隔离复测：46 行补全连续两次为 **0.647s / 0.651s**；同一真实元数据的匹配器 20 次约 **0.574s**。重复补全不是免费的，在多个候选与五个变体中会积累。历史日志也可见阶段间空档：第一轮第 3 个变体的最后来源于 08:25:23 结束，直到 08:25:29 才进入最终匹配，08:25:31 才开始下一变体。

因此，来源计时外的候选处理、逐行读音工作及其串行/回调等待是已确认的耗时组成；**未对历史三次的每段 CPU/调度等待逐一采样，不能把上表差值全部归给某一个函数，也不声称已精确量化主因占比。** 按要求，本轮没有修这段耗时逻辑。
